# 已撤回的打印连接设计草案（2026-09-20）

> 用户最新指示已否决下文的本地执行端/绕过芯烨云路线。本文仅保留历史审查记录，不是当前实施计划，不应据此增加硬件、队列架构或切换连接。当前工作限定为现有芯烨云官方接入核对与有证据的修复；未实施本文方案。

原草案状态：源码与厂家公开协议审查完成；以下是实施设计，尚未改动运行代码或上线。现场明确“始终没出纸”；任何云端成功记录都不能推翻这一事实。目标是可靠送达现有实体打印机，保持点菜、结账、票据内容、按键布局不变。

## 已证实的结构性问题

| 当前实现 | 失效方式 | 证据 |
|---|---|---|
| 厨房单跟订单一起写入 print_jobs；新订单通过 after() 唤醒一次 | 有任务记录，但执行进程结束后没有自动恢复负责人；下一笔订单只处理自己的任务 | app/api/orders/route.ts；lib/print-worker.ts |
| 手工账单直接构造内容并调用云端，不写入 print_jobs | 请求结束后没有可恢复的持久打印任务，失败仅保留审计 | app/api/tables/print-bill/route.ts |
| 云端接受即 markPrinted | 接受、云端报告完成、现场出纸混为一谈，没有送达跟踪 | lib/print-worker.ts:145 |
| 单任务原子领取 | 防止同一任务被抢走，却没有限制多笔任务/手工账单同时访问同一打印机 | lib/print-worker.ts；lib/print.ts |
| 未知结果停止重发 | 防重保护必要，但现有协议没有可靠的后续核对/恢复路径，可能永久漏纸 | lib/print.ts；lib/print-worker.ts |
| 清空队列删除原记录 | 失去逐单故障记录和待恢复依据；账单失败本来也不在队列计数中 | app/api/print/queue/route.ts |

以上是可靠性缺口，不是本次网络超时的全部根因证明。增加队列不会修复坏掉的打印机、错误的 SN 绑定或厂商设备通信问题。

## 连接方案选择

优先评估“后台持久任务 + 酒店固定打印执行端 + USB/有线局域网直连打印机”。这样最终发送到打印机的一段不再依赖芯烨云。固定执行端可以是现场已有、持续开机的合适设备；没有合适设备时才评估新增硬件，不假设酒店已有电脑。不能让每个服务员手机分别承担重试和抢占同一台打印机。

```text
现有手机 APP / 网页
        ↓ 原下单、打印账单接口
后台：保存业务 + 不可丢失的打印任务
        ↓ 酒店执行端主动通过 HTTPS 领取；可重连、可补取
酒店固定执行端：本地落盘、按打印机排队、记录发送进度
        ↓ 经型号验证的 USB / 有线局域网协议
现有实体打印机
```

Vercel 无法直接访问酒店内网设备，不公开暴露打印机端口，不把云端数据库或芯烨云密钥放入服务员 APP。执行端使用独立、仅能领取该打印机任务的可撤销凭据。

实施前必须确认打印机具体型号、可用数据接口和实际 SN 与生产绑定的对应关系。现有资料没有这些实物信息；有 Wi-Fi 不等于支持局域网直连，USB 口也不一定是数据打印口。仅凭品牌不能开发或承诺兼容。

如果机器仅支持芯烨云，则这台机器不能靠修改后台变成本地打印机。可选路线是厂家确认并修复设备绑定/固件/云节点，或用户选择支持本地连接的设备。官方确有新加坡云节点，但切换需确认账户、设备绑定和节点兼容，不能只替换 URL。单纯增加云中转仍然依赖同一个厂商打印提交/设备通道，不作为已证实修复。

## 共同的任务系统（可独立于服务员 APP 实施）

1. **统一持久化**：厨房单与账单都先保存打印任务。厨房单与原订单同事务；账单按当前桌台会话读取一致快照后保存。内容、金额、份数、版式、目的打印机都固定在任务中，重试不能重新读取后来修改的菜品和金额。
2. **一个打印机一个发送负责人**：所有类型进入同一串行队列。任务租约、执行端身份、递增 fencing token 防止旧执行端回写；实际发送还要由单一注册执行端控制。数据库锁本身不能阻止失联旧进程继续向硬件发送，不将它宣称为硬件防重。
3. **脱离请求生命周期**：持续运行的执行端负责领取、确认、断线重连和可安全恢复的任务；after() 只作为加速唤醒，不能承担最终恢复保证。关闭手机、重新部署后台不删除已保存的任务。
4. **发送前落盘**：执行端先持久保存任务 ID、内容 hash、设备身份，再尝试发送。记录“未开始、正在发送、已提交、设备报告完成、结果未知、已取消/过期”；云端报告完成与真实纸张验收分开记录。
5. **可安全恢复才重发**：明确未发送的任务可以自动恢复；已获云端订单号的查原任务，不再新建；传输中断、部分写出、发送后崩溃等无法判定的任务保留未知状态。若设备 SDK 不提供持久任务去重/完成查询，不能保证物理恰好打印一次，更不能把“socket 写成功”当成出纸。
6. **任务历史保留**：用户主动清空仍然停止那些任务，保持原有操作意义；内部改为取消并留记录，不能随后偷偷恢复。已取消、旧版本历史、已结束营业会话或超过业务时效的任务不能上线后自动吐纸。
7. **现有客户端兼容**：保留原有 API、权限、布局和打印动作含义。waitForResult=true 不能只因入队就返回原先的“云端已接受”成功结果。长期自动补打账单会与旧 APP 的人工再次点击产生歧义：现有请求没有稳定跨请求打印意图 ID；不能用“同桌/同金额”猜测两次点击是否是合法重复打印。后台可以去重同一持久任务，彻底覆盖跨点击重试则需要将稳定意图 ID 加入未来 APP，界面可不变。本轮不打包。

## 实施顺序与边界

- **第一阶段：设备能力和目的地核对**。核对生产 SN、实物型号/序列号、可用 USB/网口协议；核对云端的“已打印”到底对应哪台设备。只读检查和厂家协议资料优先，不切节点、不发旧营业单。
- **第二阶段：隔离实现**。新增兼容任务表、不可变内容快照、领取/确认 API、单执行端本地落盘/重连模块及真实传输适配器。旧自动发送保持唯一活动路径，新路径先不接生产。
- **第三阶段：控制性实物验收**。明确标记“测试，不备餐”的单张纸，使用实际型号支持的路径验证。比较正常下单、账单、断开重连、缺纸恢复、执行端重启、多手机同时下单。部分发送崩溃必须验证进入未知状态，不伪造全自动恢复成功。
- **第四阶段：单次切换**。在明确切换时间点后只允许一个路径发送新任务；不把历史失败/已清队列灌进新执行端。迁移前记录未决云任务，未知任务不自动改走本地，以免晚到双打。回滚先停止新执行端；已发送未知任务保持隔离。

## 哪些需要改 APP

| 工作 | 服务员 APP |
|---|---|
| 后台任务持久化、统一调度、目的设备校验、云端任务查询 | 可保持现有 APK |
| 固定电脑/独立设备运行本地打印执行端 | 服务员 APP 不变；需要部署并维护执行端 |
| 每个手机直接 USB/蓝牙/局域网打印 | 需要 APP 更新及权限/生命周期处理；不作为默认方案 |
| 跨多次人工点击可靠区分“重试同次打印”和“新打一份” | 需要稳定意图 ID；完整能力需客户端协议更新，不能宣称纯后台已解决 |
| 仅云端机器改为本地直连 | 软件不能凭空提供设备接口，取决于型号/硬件 |

验收是实际纸张和任务一一对应；线上 200、厂商返回 true、模拟测试通过均不单独构成交付。物理断电/缺纸期间无法即时出纸，设计目标是已提交任务不丢失、可恢复故障自动恢复、未知结果不盲目重复，且不把失败报告成完成。
