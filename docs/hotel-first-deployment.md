# 酒店点餐软件：原 Vercel 部署核对与安卓交付

## 已确认的实际基线

用户最新说明优先于此前推断：已有 Vercel Hobby 账号，原点餐软件曾在 Vercel 正常使用，下单后打印机自动打印；失败队列的清除操作也已被大家熟悉。此前“没有任何部署”“必须另建常驻服务”“应换平台或升级套餐”的迁移前提撤回。文件路径为保留已有引用而不更名。

这次工作是迁移本目录中为用户自有酒店开发的同一套软件，保留主要界面、操作顺序、连接能力和已有工作方式。原生 APK 使用同一后台，打印凭据留在服务端。用户负责项目性质及与 Vercel 的使用关系；不主动代为定性，不将条款解释转化为未经请求的工程门槛。

## 已核实的源码与历史差异

| 证据 | 观察 | 边界 |
| --- | --- | --- |
| 用户实际经验 | 原 Vercel 部署下单后自动打印 | 作为迁移验收要求；尚未由本轮工具验证线上部署 |
| `d89d3ec` | 订单提交后等待一次 `runPrintWorker(1)`，提交说明针对 serverless 打印 | 历史代码包含自动触发 |
| `0b704d8` | 改为受 `PRINT_WAKE_ON_ORDER` 控制的后台触发 | 后续发生过实现变化 |
| `ee66a93` | 删除上述触发，保留写入打印队列 | 当前源码缺少调用不等于 Vercel 原系统不能自动打印 |
| 原网页设备页与安卓设备页 | 均有确认后调用 `DELETE /api/print/queue` 的操作 | 保留熟悉的入口和规则；本轮未执行 |

清队列接口按现有行为清除 pending、printing、failed 任务。迁移不擅自改变按钮含义、增加日常操作步骤或要求员工改用新的后台工具。

本轮没有访问线上部署、连接营业数据库、清空队列或调用真实打印机。Git remote、数据库及打印配置存在不等于本地版本已经推送，也不等于线上版本不存在。必须分开核对。

## 修正后的工作顺序

1. 对照原 Vercel 可用部署所用的代码版本与当前本地提交，查明自动触发的差异；已有 Vercel 账号无需重新选择云平台。
2. 在隔离环境验证并修复必要的打印触发差异。下单成功自动尝试打印；失败保留原有处理入口。验证弱网、同键重试不重复创建订单/队列，以及清队列权限和确认操作。不得把仅“写入队列”当作自动打印通过。
3. 安卓继续沿用同一 API，对照网页核验点菜、金额、菜单、权限、退菜、结账、管理 CRUD 和 CSV 保存。完整清单见 `android-acceptance.md`。
4. 确认部署版本及配置后部署必要修复，先用受控测试单核验原打印机纸单；保留原 Vercel 配置和网页使用方式。
5. 通过目标设备验收后，绑定确认过的 HTTPS 根地址，以用户长期持有并备份的密钥制作正式 APK，验证首次安装与覆盖升级。

## 可选脚本的地位

上一轮新增的 `npm run worker:print` 仅是未启用的可选工具，不是 Vercel 安卓迁移的必需部分。没有创建对应云端服务，也没有增加费用。核对原有自动打印触发前，不开启它或与已有打印链路并行调度。使用说明留在 `printer-deploy.md`，不代表用户需要改变架构。

## 配置和回退

继续使用原后台的数据库、JWT 与打印 provider 配置，秘密只留在服务端，不写入 APK 或文档。`.env.example` 只放占位值，真实 `.env*` 被忽略。不因这次说明变更而轮换密钥、迁移数据库或重新 seed。

发布前记录可用的 Vercel 部署版本、数据库备份及兼容关系。需要回退时回到核验过的兼容版本；原有清队列按钮继续供用户按原工作方式处理队列。网页与 APK 共用后台，保留网页不能代替后台备份或恢复。
