# 点菜软件使用体验研究｜2026-09-09

状态更新：用户已授权实施 A1–A5、A8–A10、B1–B2，并新增购物车常驻数量徽标与轻量加菜反馈；明确推迟 A6 反结账、A7 折扣/服务费至后续大更新。以下保留原研究论证，已批准范围以此段为准。Web/Android 并行实现；先展示经理态本地 Web，用户确认前不提交、不发布、不升级版本。实施证据见 `pending-product-experience.md`。

- 用户反馈是当前速度快、流畅、整体约 95 分。此轮关注含义、操作位置、上下文和防误触，不重做视觉，不承诺可以客观量化为 99 分。

## 用户已经明确的前提

1. 结账与关台分开保留。结账用于确认已经收款并记账，关台有独立用途。
2. “设备”应改为“打印机”，英文同时调整；本轮只记为明确方向，不实施。
3. 对“新增菜 / Add”“已点 / Items”“已点与订单是否重复”给出明确判断。
4. 其余建议由用户确认取舍后再改代码。

## 总体判断

主流程已经合理：选桌、选菜、调整本次菜品、提交。剩余问题主要是把“本次未提交”“本桌本次用餐”“后台历史记录”放得太近、叫得太像，以及少数按钮没有准确表达操作对象和后果。

推荐做一轮小范围收口：一套中英文命名、一个本桌账单入口、连续的返回路径、清晰的金额操作。无需新增首页、复杂导航、支付平台或更多报表。

### A1、A2：名称应准确表达对象和状态

| 场景 | 现在 | 建议中文 | 建议英文 |
|---|---|---|---|
| 设置入口及标题 | 设备 / Devices | 打印机 | Printers |
| 打印状态标题 | 设备状态 | 打印机状态 | Printer status |
| 点菜页创建菜单外菜品 | 新增菜 / Add | 自定义菜品 | Custom dish |
| 自定义菜表单标题 | 新增菜品 / Add Custom Dish | 添加自定义菜品 | Add custom dish |
| 创建并进入本次草稿 | 创建并加入 / Create & Add | 加入待下单 | Add to draft |
| 自定义菜模式 | 临时菜 / 永久菜 | 仅本次使用 / 同时保存到菜单 | This order only / Save to menu |
| 底部未提交内容 | 当前购物车 / Current Order | 待下单 | Draft order |
| 未提交内容的金额 | 当前加购合计 / Current Total | 待下单合计 | Draft total |
| 已提交的本桌汇总 | 已点 / Items | 本桌账单 | Table bill |
| 汇总内菜品区 | 已点餐品 / Ordered Items | 已下单菜品 | Ordered items |
| 历史与管理模块 | 订单 / Orders | 订单记录 | Order history |
| 已收款确认按钮 | 完成 / Done（原生确认框） | 确认已收款并结账 | Confirm payment received |
| 独立关台 | 关台 / Close | 关台 | Close table |
| 结账前客单打印 | 打印收据 / Print Receipt | 打印账单 | Print bill |
| 菜单管理创建产品 | 新增菜品 / Add New Dish | 新增菜品 | Add menu item |

解释：Items 作为“餐品”并非英语错误；作为此入口名称缺少“这一桌已经下单”的含义。Add 也不是语法错误，而是无法说明是在加现有菜还是创建新菜。“自定义菜品”必须保留经理保存到菜单的现有能力，不宜简单全部改成“临时菜”。

“打印账单”表达结账前给客人核对金额，不等于已经收到款；不新增第二套打印或修改实际票据格式。本次只建议入口文案，后续确认票据用途再同步全部文案。

“待下单”的数量应注明是菜品行数，例如 `待下单 · 3项 · ₱450`。当前两端显示的是购物车行数，而非份数总和；含称重菜时不能统一叫“3份”。不必为改名新增数量计算。

来源：`lib/i18n.ts`，`app/manage/page.tsx`，`app/components/top-bar.tsx`，`app/order/page.tsx`，原生 `OrderScreen.kt`、`Strings.kt`。后续需同时检查硬编码标题和生成的原生翻译资源，不能只替换一个词典键。

### A3：合并本桌入口，保留后台订单记录

现状（两端）：三点菜单依次为已点、新增菜、订单、取消拼桌（条件显示）、结账、关台。底部固定购物车和提交订单。

“已点”查 `/api/tables/bill`，按当前开台时间查询本次用餐；“订单”进入按桌号和日期过滤的后台，默认今天，可包含该桌上一轮客人，也可能漏掉跨午夜提交的上一天订单。这不是同一份数据的两个皮肤，不能直接删掉后台。

推荐入口位置：

- 利用点菜页现有桌号/人数信息行，在右侧放文字按钮 `本桌账单 / Table bill`，点击一次进入。窄屏与放大字体容不下时，同一信息区换行，不缩小点击区域。
- 底部保持 `待下单 · 金额` 和 `提交订单`，不再塞结账或第三个同等宽度按钮。
- 本桌账单默认看菜品汇总，订单批次明细按需展开，退菜放在具体明细行。保留现有订单来源，不能只留汇总后丢掉退菜对象。
- 账单底部保留 `打印账单`、`结账`。经理需要后台调整时，提供次级 `订单详情` 入口，限当前用餐；全历史仍在设置的订单记录中。
- 三点菜单保留自定义菜品、取消拼桌（条件显示）、结账快捷入口、关台。保留结账快捷入口是照顾既有习惯；两处结账进入同一确认流程。关台与其它操作用分隔线区分。
- 不把所有操作搬到首页；不新增固定底栏。菜单外置后的点击减少来自路径推算，不是已测出的工时收益。

### A4：返回必须沿着当前任务走

现状：Web 后台订单页的顶部返回固定到 `/manage`；原生 `RdvViewModel.back()` 的管理子页也统一回 MORE。从点菜页临时查单后，返回不会直接回该桌。

推荐：记录入口来源。本桌进入详情就回本桌账单/点菜页；设置进入订单记录就回设置。保留该桌草稿、搜索词和分类；仅修复明确的上下文丢失，不重做所有导航。

来源：`app/components/top-bar.tsx`，`app/order/page.tsx`，原生 `RdvViewModel.kt`、`OrderScreen.kt`。

### A5：保留结账和关台，把语义补完整

已确认的实现事实：

- `/api/tables/checkout` 把当前开台后的可结订单记为已付款并关闭，同时关台。它是人工记账操作，不验证现实中是否已收到款。
- `/api/tables/close` 只关台；存在任何未关闭订单时拒绝。仅开台测试可关；已提交测试订单不能直接用关台绕过。
- 两端结账或关台成功都会清除本桌未提交草稿，当前确认框没有说明这一点。

推荐：保留两个独立按钮和后端基本约束。结账确认展示桌号、本次用餐、应收金额，正文 `请确认已收到款项。结账后将记录收入并关台。`；确认按钮 `确认已收款并结账`。不增加支付方式、付款对接或额外连续确认弹窗。免费早餐零金额仍允许按原规则完成，不以“金额必须大于零”禁用。

如有未提交菜品，在同一流程明确指出它们未计入账单。推荐先回到待下单处理，允许员工明确移除不需要的内容后结账；禁止静默清掉加菜。不建议自动提交草稿，因为会触发真实订单及打印。

关台确认说明 `仅关闭桌台，不记录收款。`；有草稿也需先明确处理。当前不允许未结订单直接关台的规则不变。

结账金额应取当前权威计算，并和折扣、服务费明细对应，不能把购物车金额或旧缓存直接拿来确认。现有结账 API 有自动税费处理；后续落地需要针对确认金额与最终结果的一致性做检查，本轮未确认存在实际金额差错。

需用户以后确认的一点：测试是否只指开台，还是也包括已经提交的测试订单。若包括后者，再讨论经理取消测试订单的现有流程是否足够；不得因此新增隐性“测试收入”或默认删单流程。

### A6：反结账的作用对象有实质偏差，应先修

Web/原生在历史订单卡片上显示反结账，提交的是 `tableNo`。API 查询该桌最近一次关闭的 `table_sessions`，而非点击卡片所属的那次用餐。

可推导的例子：桌 01 昨天和今天都完成了结账，当前空闲。用户在昨天订单上点反结账，后端仍会选择桌 01 最近一次关闭的用餐。此结论来自调用参数和查询条件，本轮没有实际触发。

建议把入口和操作绑定明确的用餐记录，显示日期、桌号、涉及订单及总额。仍只允许最近一次反结账时，旧记录不应显示可执行入口，服务端也应校验具体记录；不能仅改按钮名称。保留经理权限、原因填写与审计，不扩展历史任意反结账权限。

来源：`app/manage/orders/page.tsx` 的 `reverseCheckout`、原生 `ManagementScreen.kt`、`app/api/tables/reverse-checkout/route.ts`。

### A7：金额按钮要先说明会调整多少

现状：两端“折扣”“服务费”点击即 POST，仅传类型。API 没有数值时选第一条启用规则，有多条时由排序决定；无规则则失败。不能把它当成已实现自由输入金额，也不能误报为必然报错。

推荐一个轻量表单/确认层显示当前规则、比例或金额、调整前后金额，再确认应用。已应用规则明确显示，不让员工重复点了却看不出变化。首批不扩展随意折扣权限；是否支持手动输入和选多个规则可后续决定。

来源：两端订单管理与 `app/api/orders/[id]/charges/route.ts`。

### A8：退菜与删除应区分操作强度

现状：本桌账单退菜会询问数量；后台订单详情中的“退菜”两端均直接退 1、原因 `manual`。相同按钮在两个地方点按后果不一样。订单删除又与常规金额调整一起出现在卡片上。

推荐：统一用具体菜品、原订单行、数量、确认动作的退菜层，默认数量可为 1。日常取消用取消订单，删除保留经理能力但移入该订单的更多操作并维持明确确认。不删除已有业务能力。

### A9：打印机页从工程诊断页变成日常管理页

现状：首屏有打印部署就绪、Primary/Fallback、环境变量名称、路由词、队列、自检、清队列；设备卡还有人工“设为在线”等操作。`ready` 是配置就绪，不能解释成打印机确实出纸。

推荐首层按后厨、吧台呈现打印机状态、状态时间、待打印/失败数量、`打印测试单 / Print test page`。现有数据不足以证明在线时显示未知或明确是记录状态。高级诊断收起保存现有技术信息和人工状态操作；不凭标签改动伪造探测能力。

重试打印明确是处理队列中的任务，不暗示只补打眼前那张订单。清空队列收进维护操作，确认说明将停止哪些尚未完成的打印任务。首批不新增批量重试策略，不触碰历史队列。

来源：`app/manage/devices/page-client.tsx`、原生 `ManagementOps.kt`、`lib/i18n.ts`。打印机页面的细节布局需要后续原生视觉核对，本轮主要核对源码。

### A10：报表名称与状态不要混淆收款

订单页把所有查询到的订单金额相加，叫“营业额 / Revenue”，含未结订单；收入接口仅算 paid/closed 且未取消、未并入的订单。两个数字可能合理地不同，但当前名称让人以为是一种金额。

建议订单页改 `订单金额 / Order total`，收入页保留 `收入 / Revenue` 或更明确的 `已结账收入 / Settled revenue`。不变更统计口径。收入目前按订单创建时间归属日期，不是收款时间；如希望看收款日收入，这是另一个需确认的业务改动，不能偷偷随改名一起调整。

已点明细两端直接露出 submitted 等状态，订单列表仅翻译部分状态。统一根据业务状态与 cancelled_at、付款信息等映射显示。不能把所有 closed 一概改成“已收款”：关闭也可能来自取消等操作。金额调整类型同样使用中英文业务名。

## 可选小功能，不建议为了加分堆功能

- B1 修改用餐人数：当前人数在开台时选定，点菜页没有明显修改入口。若酒店常有中途加人，允许点人数修改比关台重开合理；需先确认其是否影响免费早餐资格或统计，不能假定只是改文字。
- B2 购物车编辑选项：目前选错饮料或肉类通常需移除再选。可在该条目提供编辑选项，重新计算价格，保留备注；区分不同配置、保持草稿和提交幂等性。属于增强，不是当前订单选项功能失效。
- 不建议本轮加会员、营销、支付集成、厨房看板、更多图表、手势快捷操作。现有速度、分类、编号搜索、底部提交、独立关台、强制更新和连接恢复方式继续保留。

## 后续确认与验收方式

用户可以按 A1–A10、B1–B2 逐项选择做/不做；这份记录不自动授权实施。推荐先处理 A6，再把 A1–A5、A7–A8、A10 合成一个小批次，A9 与可选功能视实际使用频率取舍。

确认实施后采用少量代表场景：服务员英文界面从开台到加菜，查看本次账单后返回；经理核对折扣及结账金额；空台测试关台；有草稿时尝试结账；从旧订单尝试反结账。Web/原生保持相同业务语义，金额与会话操作用隔离 fixture 检查，小屏只检查变更区域。不重复整套无关测试，不为这份文档打包 APK。

真正接近“99 分”的判断应是员工能否不解释就选对入口、准确说出按钮后果、完成常用流程；当前尚无现场计时或误操作数据，不能给本次研究制造量化提升。
