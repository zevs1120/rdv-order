# RDV 原生安卓迁移计划（待实施）

日期：2026-09-07。代码评估基线：`ee66a93`。本文是实施方案，不代表安卓版本已经存在或上线。

## 1. 目标与建议

采用 Kotlin + Jetpack Compose 开发真正的原生安卓客户端，继续连接现有 Next.js API、PostgreSQL 和服务端打印系统。

本次迁移的验收目标是：员工仍按原来的位置、顺序和规则完成工作；同样的业务输入得到同样的订单、金额、桌台状态和打印结果。保留网页端，与安卓端共用一套数据。

原生客户端需要重新实现 React 页面、CSS 样式、浏览器状态和交互逻辑；不能把现有 TypeScript 页面直接编译成 Kotlin 界面。现有 API、数据库、打印服务、文案、视觉参数、业务样例及服务端测试可继续使用。服务端计算保持权威，安卓不另建一套结算规则。

WebView 封装能够较快得到可安装的 APK，但页面仍是网页，因此不作为本计划的原生交付方案。原生化本身也不解决服务器或打印机网络故障。

## 2. 已核实的现状与待核实项

已阅读页面、关键 API、鉴权、请求封装、缓存、打印、日期及数量处理代码。现有测试运行结果为 19 个测试文件、57 项测试全部通过。测试包含模拟数据库等依赖的测试，不等于实际数据库、部署环境、打印机已完成联调；本次没有进行生产下单、打印或部署。

## 4. 安卓工程需要补齐的能力

建议先在独立 `android/` 工程中实现，按功能组织页面；建立 UI、页面状态和数据访问层。初期不做与迁移无关的大规模后端拆分。

| 原有能力 | 安卓实施内容 |
| --- | --- |
| React 页面和组件 | Compose 页面及 RDV 自定义组件；Kotlin 实现客户端筛选、校验、数量和备注逻辑 |
| Next.js 路由和 URL 参数 | 原生导航栈，保留桌号、人数、筛选条件和返回去向；系统返回先处理键盘/弹层再返回页面 |
| Fetch 与相对 `/api` 路径 | 统一 HTTPS API 客户端、明确 base URL、请求/响应模型、错误解析、超时和取消处理 |
| JWT / localStorage | 继续使用现有 Bearer token，保留现有登录有效期规则；使用 Android Keystore 保护本地加密所用密钥，不保存 PIN |
| session/localStorage 和 PWA 缓存 | 本地偏好与持久化存储；分别定义菜单、草稿、最近桌台和临时快照的有效期及清理时机 |
| 页面内存状态 | ViewModel 管理页面状态；需跨进程存活的草稿和待确认请求持久化，避免只放在 ViewModel 中 |
| navigator 网络状态 | 原生网络监测结合请求结果；连上 Wi-Fi 不等于 API 可达 |
| alert / confirm / prompt | 等价原生弹窗，保持提示、默认值、验证、确认/取消作用 |
| CSV blob 下载 | 使用 Android 文件保存能力承接相同 CSV 内容、文件名与导出入口，验证导出后文件可找到、可打开 |
| Service Worker | 以原生缓存替代；保留断网可查看缓存/保留草稿的范围，不自动增加离线下单和后台补单 |
| 网页部署更新 | 签名 APK、包名、版本号、分发和升级流程、签名密钥保管、兼容已安装版本的 API |

认证、数据库和打印 provider 的服务端密钥继续留在服务器，APK 只包含客户端连接所需配置和用户登录态。初版不引入蓝牙/USB 直连打印，也不将服务端打印 worker 搬到手机；否则会改变当前已接通的链路。

浏览器的登录态和未提交草稿不能假定可直接被原生 APP 读取。切换设备时完成或核对原购物车后重新登录；已提交订单和账单仍从同一后端取得，不需要复制生产业务数据。

## 5. 必须专项验证的等价性

1. **提交超时与重复点击**：现有点菜页下单超时设置为 12 秒、自动重试为 0，同内容待处理键可在 10 分钟内复用。安卓不能给所有写接口统一增加自动重试。保存待确认的原始载荷、桌台、账号和幂等键；结果未知时保留购物车，手动重试复用同一操作身份。进程被杀后恢复也不应生成另一笔相同订单。需要补充状态查询能力时，单独评估最小兼容接口，不默认已具备。
2. **开台、退菜、结账、打印的独立策略**：逐接口记录现有超时/重试、重复操作行为和提示。它们不都具备下单同等的幂等能力，不能套用同一个重试策略。
3. **成功回执与真实结果**：订单保存、打印任务入队、打印服务接收、纸张实际打印分别核验。不能将“下单成功”当成“打印成功”。
4. **金额与数量**：服务端金额为权威，保持当前单位、舍入和 PHP 展示；客户端用相同样例比对。海鲜 `qty=3` 在 100g 类菜品中显示 300g，不能发成 300 份；按只计量也需独立验证。
5. **日期**：区分现有日期预设与自然月导出；例如现有 `month` 预设使用回推一个月逻辑，不擅自改成当月。`tzOffsetMin` 必须沿用 JavaScript `getTimezoneOffset()` 的符号，UTC+8 对应 -480，不能直接发送原生时区的 +480。
6. **缓存与草稿**：按桌保留购物车及备注，覆盖切桌、切分类、退后台、锁屏、进程回收和重新开台；核实过期草稿处理，防止上一轮桌台内容混入新订单。退出/换账号时隔离本地数据。
7. **多端共用**：网页与安卓共用同一账号/菜单/桌台/订单，覆盖同时开台、同时点菜、结账与提交竞争。保持现有刷新入口和时机；不将桌台每分钟更新时间误当成服务器状态轮询。
8. **应用生命周期与文件**：长时间运行、系统返回、软键盘遮挡、低内存恢复、覆盖安装、导出失败/取消和文件可访问性均需实机验证。

## 6. 分阶段实施与交付

下列工期是本次代码评估后的初步工程估算，不是固定承诺。假设一名熟悉 Kotlin/Compose 的开发者为主，有业务验收人员和后端联调支持，线上版本、目标手机和测试打印机可提供；按工作日计算。

| --- | --- | --- | --- |

| C：营业主流程 | 开台、菜单、特殊菜/备注、购物车、提交、账单、打印、退菜、结账、拼桌 | 一套从登录到关台的完整实机流程，业务和打印结果一致；仅作内部阶段包 | 8–12 天 |

C 阶段包只用于验证主流程。正式替换营业使用必须等 D、E、F 完成，不能因经理功能较少使用就省略。

## 7. 验收和上线门槛

建立 `功能 → 原页面/操作 → API → 预期数据/纸单/文件 → 安卓实现 → 验收结果` 台账。每项应有操作步骤、截图或录屏、脱敏请求和结果证据。

- **页面与操作**：所有确认保留的页面、弹层和入口均覆盖；员工按同一任务走同样步骤，不需要重新学习按钮位置。
- **业务结果**：使用相同初始状态的独立测试桌台/数据集，对照菜品、备注、数量、费用、订单状态、桌台状态、权限和导出内容；金额和数量逐项一致。打印结果忽略必要的测试单号/时间差后对照内容、目标与份数。
- **服务端兼容**：现有服务端测试继续通过，补齐关键接口请求/响应契约和真实数据库集成验证；任何必要服务端修改都要验证旧网页与已安装安卓版本。
- **安卓验证**：针对客户端业务规则的单元测试、关键 UI 流程自动化及真实设备测试。重复提交必须验证只有一笔订单和相应的一次队列入队，纸单还要另测。
- **性能**：阶段 A 在实际设备记录启动、打开桌台/菜单、搜索、提交结果可见的基线；安卓在相同网络和数据量下不出现可感知退化，关键耗时按双方确定的基线验收，不在未知设备上承诺固定毫秒数。
- **现场连接**：实际打印 provider 和打印机、厨房单/客用账单、断线重试、经理设备页面的状态都完成实测。
- **发布**：包名、最低支持 Android 版本、目标 SDK、签名与更新渠道确定；覆盖安装保留必要状态，数据不丢失。若经商店分发，发布时再核对当期要求。
- **回退**：先保留网页入口，安卓问题发生时核对待确认订单并回网页继续营业；不回滚已产生的营业数据。APK 降版本不可假定能直接安装，优先用更高版本号发布修复包，另行验证安装兼容性。

试用先覆盖少量设备，确认稳定后再扩展。对于账单错误、重复订单、漏打印、权限错误、草稿串桌和流程阻断，未解决前不全量替换。

## 8. 下一步所需信息与当前边界

开始 A 阶段时收集：

1. 目前实际使用的网址及部署版本、所有仍在使用的功能入口。

4. 分发方式：店内 APK 安装、设备管理系统或应用商店；暂按店内受控安装做估算。
5. 实机和打印联调窗口，以及一名服务员和一名经理的验收安排。

当前交付仅为计划文档；没有创建安卓工程，没有修改应用代码、数据库、打印配置或部署。下一步应先完成现状基线，再制作可运行且可对照的三页原生样板。
